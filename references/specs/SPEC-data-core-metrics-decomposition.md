# SPEC: Modular Decomposition into Data, Core, and Metrics

## Problem Statement

Currently, `mltreelib` concentrates tabular data ingestion, categorical encoding, grouped and temporal transformations, synthetic ground-truth benchmark generation, model evaluation metrics, and tree/anomaly algorithms into a single monolithic core library. 

This monolith creates distinct points of friction:
1. **Coupled Development Velocity**: Modifications to calibration metrics or categorical encoders trigger recompilations and integration tests across the heavy tree learning engines and PyO3 bindings.
2. **Lack of Independent Reusability**: Machine learning practitioners and researchers cannot use the rich tabular encoding layer (`CatBoostEncoder`, `WoEEncoder`, `IndexMapper`) or the diagnostic evaluation surface (`Metrics`, double lift, calibration curves, PSI) independently without carrying the entire tree algorithm suite.
3. **Cognitive Overhead**: The library surface conflates data engineering, statistical validation, and tree structure search, making it harder for contributors to maintain focused mental models and test boundaries.

## Solution

Decompose `mltreelib` into three cohesive, independently versioned, and cleanly bounded components across both the core engine and the Python surface:

1. **`data`**: Tabular ingestion, schema inference, categorical index mapping, high-cardinality encoders, grouped scalers, calendar/time transforms, and synthetic ground-truth data generation.
2. **`metrics`**: Comprehensive model diagnostic curves, calibration analysis, probability ranking evaluations, population stability index (PSI), and decile profiling.
3. **`core`**: Decision tree and model tree learning engines, split criteria, surrogate routing, explainer algorithms, and base anomaly detection trees.

Existing imports at the root level (`from mltreelib import ModelTree, Metrics, DatasetBuilder`) remain fully supported via backward-compatible facade re-exports, while new modular namespaces (`mltreelib.data`, `mltreelib.metrics`, `mltreelib.tree`, `mltreelib.anomaly`) allow targeted usage.

## User Stories

1. As a tabular data engineer, I want to use `mltreelib.data` encoders (such as TargetEncoder and CatBoostEncoder) independently, so that I can preprocess features for external linear or neural models without pulling in tree algorithms.
2. As a model risk validator, I want to import `mltreelib.metrics` as a standalone evaluation package, so that I can compute calibration curves, population stability index (PSI), and double lift on predictions generated by any model family.
3. As a tree algorithm researcher, I want tree learning algorithms isolated in `core`, so that experiments with predictive clustering trees or split heuristics do not risk regressions in data transformation or metric calculations.
4. As a package developer, I want changes in evaluation metrics to compile in seconds without rebuilding the tree fitting engine, so that my development iteration loop remains rapid.
5. As an existing library user, I want top-level imports from `mltreelib` to continue functioning identically, so that my existing notebooks, pipelines, and benchmark scripts do not break.
6. As a benchmark engineer, I want to use the synthetic benchmark generator from `mltreelib.data` with known ground-truth manifests, so that I can test structure recovery against external baseline packages.
7. As a low-resource or edge deployment developer, I want to deploy only the scoring runtime and tree predictor without the generator and complex feature encoders, so that binary size and memory footprint are minimized.
8. As a CI/CD engineer, I want isolated test targets for data, metrics, and core, so that parallel continuous integration jobs can fail fast on domain-specific boundaries.
9. As an R package developer preparing future bindings, I want a decoupled C-ABI / FFI boundary for data structures and metrics separate from tree learners, so that extendr bindings can be mapped progressively.
10. As an anomaly detection researcher, I want base anomaly trees organized under a dedicated anomaly sub-namespace within core, so that density trees, isolation trees, and contextual auditors are logically grouped.
11. As an API consumer, I want clear type signatures and documentation organized by domain responsibility, so that exploring auto-complete in my IDE is intuitive.
12. As a data scientist working with temporal tabular data, I want to access calendar parts, trended transforms, and day lags from the data module, so that feature engineering pipelines are decoupled from model training.
13. As an audit and governance officer, I want to run subgroup and contextual audits using GritBot independently on production data, so that compliance reporting does not require loading training or optimization pipelines.
14. As a test author, I want unit tests for metrics to depend only on true values and predictions rather than fitted tree instances, so that tests remain fast, deterministic, and isolated.
15. As an open-source contributor, I want smaller, single-responsibility crates in the workspace, so that reading and contributing to the codebase does not require understanding all domains simultaneously.

## Implementation Decisions

### Architectural Separation
- The project will adopt a three-pillar architecture: `Data Layer`, `Metrics Layer`, and `Core Learner Layer`.
- The Python package will expose explicit subpackages:
  - `mltreelib.data`: Encoders, DatasetBuilder, IndexMapper, VariableScaler, GroupedScaler, calendar_features, decomposed_transform, trended_transform, windowed_transform, lag_by_days, generate, list_datasets, load_dataset.
  - `mltreelib.metrics`: Metrics class, calibration routines, curve computation, classification and regression scoring, pairwise distance diagnostics.
  - `mltreelib.tree`: ModelTree, LeafControl, winnow, and associated pruning/routing utilities.
  - `mltreelib.anomaly`: GritBot, DensityEstimationTree, ExtendedIsolationTree, HalfSpaceTree, RandomCutTree, ActiveAnomalyTree, ContextAnomalyTree.
- The root namespace will re-export all public symbols for backwards compatibility.

### Rust Workspace Partitioning
- The Rust workspace will transition from a single monolithic core crate into three specialized workspace members:
  - An ingestion and preprocessing crate responsible for frame memory representation, schema inference, categorical encoding algorithms, grouped/temporal transforms, and synthetic benchmark generators.
  - A metric evaluation crate responsible for statistical distributions, calibration calculations, rank-order metrics, and distance measures, free of any tree dependencies.
  - A tree learner crate responsible for split finding, surrogate routing, linear leaf refitting, and anomaly tree topologies, consuming the data crate for input frames.
- A unified PyO3 binding crate will aggregate the specialized crates and expose the Python native extension.

### Zero External Dependency Constraint
- The architectural split preserves the strict constraint: **no scikit-learn dependency**.
- Arrow/Parquet interoperability will remain clean and zero-copy via PyArrow / Arrow-rs, while Pandas is strictly an optional consumer.

### API Contracts
- Data transformation components adhere to standard `fit` / `transform` / `fit_transform` contracts without inheriting from scikit-learn base classes.
- Metrics expose both static functional calculations (e.g. `roc_curve(y_true, y_score)`) and structured report generators (`classification_report`, `decile_profile`).
- Tree and anomaly models adhere to `fit` / `predict` / `anomaly_score` contracts.

## Testing Decisions

### Seam and Scope
- Tests must verify external behavioral contracts only; no test may pin incidental private struct fields or intermediate internal buffers.
- The primary test seam is the public module boundary:
  - Data module tests verify that input data transformations match hand-verified ground truth, that unseen categories are mapped deterministically according to policy, and that missing values never cause panics.
  - Metrics module tests verify statistical accuracy against known mathematical identities (e.g. perfect forecaster calibration is diagonal, ROC-AUC of separated classes equals 1.0, PSI of identical distributions equals 0.0) without constructing tree models.
  - Tree and anomaly module tests verify structure recovery on synthetic data and expected isolation / density bounds on real tabular datasets.

### Prior Art
- Existing behavioral test suites in `tests/builder.rs`, `tests/encoders.rs`, `tests/features.rs`, `tests/metrics.rs`, `tests/anomaly.rs`, and Python pytest suites serve as the direct specification and oracle for the decomposed components.

## Out of Scope

- Implementing ensemble or forest wrappers (e.g. Random Forest, Isolation Forest ensembles) during the component split.
- Introducing scikit-learn as a build or runtime dependency.
- Implementing R bindings (extendr) in this phase.
- Automated feature engineering pipelines (Featuretools style).

## Further Notes

- Execution will follow a staged rollout:
  1. Phase 1 establishes the Python subpackage namespace hierarchy with root re-exports, leaving Rust internals unchanged.
  2. Phase 2 partitions the Rust Cargo workspace into modular member crates.
- Version bump cadence continues at micro increments per small unit of verified work.
